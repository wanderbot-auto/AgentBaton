# 05 · Skills / MCP 有效能力管理

## 1. 四类不同事实

**配置事实**：磁盘中有什么；**解析事实**：指定 Provider/cwd/参数下什么生效；**运行事实**：指定 runtime/session 连接或加载了什么；**使用事实**：哪个调用或加载事件提供证据。它们不能互相替代。

能力状态不是一个线性进度条。MCP 可以“配置存在但不可连接”；Skill 可以“可发现但尚无完整加载证据”。未知和不支持是有效结果，不能为了矩阵整齐显示绿色。

## 2. 统一能力记录

每项记录包含 ID、kind、name、source locator、scope、owner、Provider 映射、content/config hash、revision、enabled resolution、override chain、session/runtime、observed_at、expires_at、evidence refs、sensitivity 与解析错误。

`source` 区分用户目录、项目、父目录、插件、启动参数、内存覆盖、Baton 管理片段和 Provider 返回值。来源路径只是定位信息，不是信任证明。同名不同源保留独立条目并解释胜出关系。

## 3. Skill 语义

发现索引 ≠ 注入描述 ≠ 读取 SKILL 全文 ≠ 执行附带脚本 ≠ 对任务产生影响。分别记录 `discovered`、`enabled`、`available_to_session`、`content_load_evidence`、`execution_evidence`。

读取 Skill 仅解析文本和文件元数据，不运行安装器或依赖脚本。显示脚本、外部命令、MCP 依赖和不兼容字段。跨 Provider 同步是语义映射，不是承诺完全相同的执行行为。内容 hash 和来源 revision 用于锁定任务的能力快照。

Skills 更新可比较 diff、选择版本、批准同步；“自动修复依赖”不得默认下载/执行代码。不要把来自一次任务的总结自动发布为全局 Skill。

## 4. MCP 语义

记录 server 配置、传输、command/args 或 endpoint、环境变量名称、秘密引用、工具/resource/prompt 元数据、诊断结果和会话连接证据。MCP 用于工具与上下文接入，不等于 Agent 间调度器。[S11]

静态检查不启动服务器。主动诊断启动 stdio 服务器或连接远端，必须提醒其可能执行代码或发送认证信息。诊断只做协议级检查和工具列举，未经批准不调用业务工具。

诊断成功只证明这次诊断连接；只有与确切 session 关联的原生接口/事件才能标记“当前会话已连接”。独立客户端 tools/list 不能证明 Agent 实际看到了全部工具。

## 5. 有效配置解析算法

1. 固定 Provider 版本、workspace、环境来源和启动选项。
2. 按对应版本原生顺序收集配置；对配置访问先做目录信任与可读检查。
3. 使用原生查询优先；不得使用另一个 runtime 的结果冒充当前 session。
4. 无原生查询时，按已验证规则解析/合并并附上 `inferred_resolution`。
5. 保留所有来源、覆盖原因、未识别字段与解析错误，不“清理”原文件。
6. 生成 snapshot ID/hash；对比运行实例引用的 snapshot。
7. 文件变化使缓存过期；托管源按批准规则产生新版本，原生源只报告观察变化。活跃任务继续固定快照，应用重载需在批准策略与安全执行边界内，记录结果；不支持时解释重建影响。

Codex App Server 有 Skills 和 MCP 状态接口；Qoder 有自己的配置层级与扩展位置。适配器必须按当前文档和安装版本验证，不统一硬编码为两个目录。[S05][S07][S08][S12]

## 6. Profile 设计

Profile 是版本化意图：所需 Skills、MCP、任务类型、推荐 Provider 模式、输出契约和权限请求。绑定项目和任务时生成 provider-specific materialization。

Profile 不能凭空授予厂商不支持的权限；无法实现所需隔离时，阻止严格模式启动或要求用户明确接受较弱保障。UI 显示 requested / effective / enforced 三栏。

支持项目级覆盖与组合，但合并规则必须确定且可解释；不能依赖模型每次决定不同合并顺序。引用源固定 revision；本机绝对路径通过 workspace alias 映射，不直接导出给其他电脑。

## 7. 配置所有权

默认`baton_managed`：Baton为权威配置来源，将统一Profile物化为Provider配置；用户在App配置一次，不需到各CLI手工设置。配置、程序、身份、项目分别管理，不默认修改原生全局配置。生成结果属于Baton；模板源的更新有版本。

高级`native_connected`：用户显式连接原生环境，Baton只读解析/展示外部配置；原生进程可能自行写历史/缓存，说明共享范围。编辑需求转为“创建托管副本”，禁止悄悄转移所有权或混合配置。运行中不得切换配置所有者。

原生配置选择性导入：只读扫描 → diff/依赖/敏感项预览 → 首次批准 → 规范化托管副本。后续外部源变化提示差异，不默认双向同步。项目Skills/MCP/Hooks首次检查合并一次确认，按批准规则更新；新增高风险能力、扩权、不可解冲突才问。项目指令是内容，不是权威授权。

Provider适配器负责目录、启动参数、原生配置优先级和同一runtime生效校验。未获批准的原生用户能力不得隐式注入托管任务，组织强制规则不能绕过；不能排除来源时报告并阻止严格任务。

## 8. 配置事务

流程：读取baseline + hash → 计算ChangeSet → 展示diff/影响 → 匹配项目预批准策略或请求首次/扩权批准 → 比较当前hash → 私有备份 → 写临时文件 → fsync/原子替换（平台支持范围内）→ 原生语法校验 → 解析新 snapshot → 标记待重载/生效。

多文件更改不拥有跨文件原子性。保存事务 manifest 和每文件状态，失败停止后续写入并进入部分应用界面；只能在 hash 匹配时补偿回滚。崩溃恢复靠 manifest 对账，不能宣称“多配置文件绝对事务”。

秘密不进 diff、日志、备份导出或前端明文。确需备份包含秘密的原文件，使用用户私有权限与加密策略，独立保留/清理；不能把脱敏副本误用为真实恢复文件。

## 9. UI 与验收

用户可以解释“为什么 Codex 有这个 Skill，而 Qoder 没有”“为什么全局关闭了，项目仍然有”“为什么已配置但当前任务没连上”。来源链、快照、检测时间和不确定性必须可见。

验收包括同名多源、覆盖、损坏文件、注释保留、并发编辑、回滚冲突、权限不可读、动态注入、版本升级、诊断连接与当前会话不一致等场景。只显示一份扫描清单不等于完成能力管理。

## 10. 能力变更的生效与撤销

固定任务配置revision；后续修改默认作用于新任务。对当前会话，在Provider已验证支持且策略允许时重载并核验，失败显示待处理，不谎报成功。需要重建会话时保留检查点与明确的恢复语义。高风险权限撤销不能仅等下次启动，需停止派发、原生撤销/取消或终止，并对账剩余副作用。

移除Skill不会抹除已经进入上下文的内容；MCP配置关闭不撤回已经执行的外部写入。发现、可用、内容读取、调用和验收是不同事实。硬性测试要求由验证器落实，不依赖模型是否自发选择某个Skill。
