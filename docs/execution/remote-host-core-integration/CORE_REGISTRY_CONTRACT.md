# RHOST-002 Core registry contract proposal

Status: docs-only proposal for leader/A Host19 DDL reconciliation, not an implemented API, migration or final schema allocation. Audited accepted Core is a4e03303b54bd5a5544131e95ad39662f8310e29; pure registration source is frozen at cb5bfd1ed856dd6d3d30f190b867692411cee2f7. No Core, schema, dependency, lock, native or UI edits are authorized by this document. RHOST002A validation and transport behavior remain unchanged.

## Typed request and immutable creation receipt

Use the existing authenticated, versioned IPC envelope and ordinary actor scheduling. Authenticate owner token, API version, bounded request ID and method/envelope before accessing Host records. Request ID correlates a response; it is not the durable idempotency key. Token rotation must not change the durable key scope. Host methods must not be exposed through scoped Provider/model handles or an early scheduler bypass.

| Proposed method | Closed params | Envelope rules | Result |
| --- | --- | --- | --- |
| hosts.register | The frozen HostRegistration schema_version=1 object directly | Required idempotency_key; expected_revision must be None | Immutable HostCreationReceiptV1 |
| hosts.find_registration | {key} | No envelope idempotency_key or expected_revision | found with the original receipt, or absent; integrity/storage failures are errors |
| hosts.get | {host_id} | No mutation envelope fields | HostRegistrationViewV1 or NOT_FOUND |
| hosts.list | {limit, after_created_sequence} with optional cursor | No mutation envelope fields | Bounded records and next cursor |

The create key is nonempty, at most256 ASCII bytes from [A-Za-z0-9._:-], and is a nonsecret opaque client token. Its database scope is the fixed method/version hosts.register:v1 within this owner-authenticated Core Store, not the rotating token, project, Provider identity, request ID or expected remote Host ID. UI/native must retain the key plus exact submitted metadata through an ambiguous outcome. A new IPC request ID with the same creation key is normal recovery.

The existing envelope represents expected_revision as Option: None (including the current decoder's absent/null equivalence) is required for create/reads; Some(0) is not create authority. Params reject unknown fields. The existing Core envelope parses params into serde_json::Value: retain its existing raw IPC frame limit, bound the serialized params to16KiB before typed Host decoding, and validate with the frozen pure validator before persistence. Core must not pass serde-only values around validation. The foundation decode_registration helper independently bounds its actual raw byte input before parsing; reserializing an already parsed Value does not prove the original params byte span was16KiB (whitespace/key-order bytes differ). An exact raw-params-span limit would require explicitly scoped preservation of raw params; do not silently claim that extra parser change is implemented. Unknown/oversized metadata still fails before persistence. Status, IDs, revisions, sequences and authorization fields are never accepted inside HostRegistration.

Canonical payload comparison is exact serialization of the typed validated v1 object in a fixed field order, with all optional/default behavior versioned. JSON whitespace/object-key order does not create a different operation; names, reference strings, case, mapping order and roots are not normalized, sorted or rewritten. No input payload includes the key or request ID. Save the canonical payload itself in existing idempotency.payload; a digest alone must not replace equality. Golden bytes and replay fixtures must pin this encoding before implementation acceptance. V1 encoding/validation semantics must remain available for durable replay after upgrades; schema_version changes require an explicit version contract, not silent reinterpretation.

Proposed immutable HostCreationReceiptV1 fields are receipt_version=1, host_id (Core UUID), revision=1, created_sequence (positive committed events.sequence), created_at (server event timestamp), and registration (the exact validated typed metadata). Receipt contains no live status or probes. Persist its encoded result in existing idempotency.result and return the same decoded receipt on replay. Never recalculate UUID, sequence, timestamp, validation result or current status on replay. The per-request outer response envelope may have a new request ID; its receipt value stays equal. Use sequence/revision for ordering; wall clock is descriptive, not a lease/budget/identity guarantee. Clock rollback does not create a new registration or expire its receipt.

There is no update/delete method in this cut. A create with an existing key and changed endpoint, pin, identity, configuration, mappings or name is CONFIG_CONFLICT. A different key is another create, subject to name/capacity rules, never an upsert. Future edit/removal needs its own expected-revision, stable-key, identity-drift and history contract; registration cannot replace an active binding or authorize contact.

## Fixed DDL, record and encoding proposal after leader decision

Leader approved the engineering contract (not product write scope): the exact six-column/nonunique-index DDL is registry-contract/ddl.sql, matching A406be16 ADR-001 bytes. registry-contract/CONTRACT.json pins its SHA-256, complete required field orders/types/constants and synthetic canonical fixtures. These files specify a proposal, not executed SQL or a produced database/receipt.

Host document required ordered fields: record_version=1, id, revision=1, created_sequence, created_at, creation_key, registration, creation_facts. Receipt required ordered fields: receipt_version=1, host_id, revision=1, created_sequence, created_at, registration. Event payload required ordered fields: payload_version=1, host_id, revision=1, creation_key, registration_sha256. All nested objects are closed; no omitted/null/default fields. Metadata uses exactly the frozen schema1 field order and required fields, including directory_mappings even when empty. creation_facts required ordered fields/constant values are local_validation=configuration_syntax_validated, references=unresolved, remote_probe=not_probed, remote_connection=not_contacted, remote_capabilities=unknown, execution_enabled=false. They explicitly snapshot creation scope, are never contact observations and are not replay-derived live state.

Encode with typed serde_json compact UTF-8, no BOM/newline, field declaration order, original array order, standard serde_json escaping, decimal integers and no name/reference/path transformation. Generic Value/map serialization is not the canonical v1 encoder. Payload is the typed registration encoding; idempotency.result is the typed immutable receipt encoding, not a Host view. Store their exact strings; event payload registration_sha256 is lower-hex SHA-256 of canonical metadata, an integrity comparison only, not authority or a substitute for full payload equality. Fixed synthetic golden fixture hashes are pinned in CONTRACT.json; a future implementation must prove serializer output equals those bytes and preserve v1 encoding thereafter.

Core generates one lowercase canonical UUID-v4 Host id, one separate event UUID and one existing storage::now() RFC3339 timestamp only after replay/admission, copying that timestamp to event.occurred_at, record.created_at and receipt.created_at. Actual inserted SQL sequence must be a positive integer no greater than9007199254740991 so native/JS reads cannot round it; out-of-range create rolls back, and a persisted invalid/out-of-range mirror fails closed. Sequence is SQL INTEGER with a stricter application/wire bound, not an extra DDL CHECK. No fake sequence1 or MAX lookup. Event document retains the existing pre-insert sequence0 convention; its row key alone supplies created_sequence. Event aggregate_id=host UUID, revision=1, kind=host.registered, source=user_action and the exact closed payload above must agree with row/document/receipt mirrors.

Concrete local limits: metadata16KiB, serialized Host document24KiB, serialized immutable receipt24KiB and serialized creation event4KiB. Enforce raw persisted byte limits before JSON decoding, including values read from generic idempotency. The mandatory integrity scan reads no more than129 rows; any129th means error. Within128 rows, validate all Host documents/mirrors/creation keys and directly fetch each referenced creation event and exact hosts.register:v1 receipt/payload (bounded per value) in the same snapshot; missing/malformed/version/duplicate/linkage mismatch is an integrity/OUTCOME_UNKNOWN error before a new-create capacity decision. Worst admitted Host document decoding is3MiB, plus at most128 bounded event/receipt/payload reads; stream/check cumulative bounded bytes and query count instead of accumulating arbitrary DB values. Invalid oversized values fail before allocation/parse; do not rely solely on LIMIT. This bounded audit is not a guarantee against arbitrary offline deletion of all three domains, and does not scan unrelated events. Absent remains the stated successful snapshot outcome, never proof that an in-flight request cannot commit.

For mutation, that scan and every replay/admission/write step use the SAME IMMEDIATE transaction, never a preflight read followed by another transaction. For find/get/list, use one read transaction/snapshot, retaining consistent row/event/receipt links without modifying or dropping any pins. A capacity error must not hide an intact prior receipt. For list, honor25 records AND512KiB including response framing: stop before a record would exceed bytes, return a continuation from the last returned sequence and make progress. A malformed/oversized record is an error, never silently skipped. Count/byte limits are proposed engineering constraints awaiting real tests, not observed latency guarantees.

Persisted strict types reject duplicate fields, unknown fields, wrong integer/floating/string/bool/null types and unsupported versions in the typed raw document/receipt/payload decoder. The existing IPC params=Value parser may already lose duplicate-key or numeric lexical information: do not claim it rejects original duplicate params keys or lexical1.0 solely by reserializing Value. Follow existing envelope semantics, reject observable wrong types, and preserve raw params only under an explicitly scoped future parser change. This distinction does not weaken strict persisted decoding or foundation raw decode_registration tests.

Final transaction order is authentication/bounds/typed validation outside SQL; begin IMMEDIATE; bounded integrity/key reconciliation; same-key conflict or original receipt return; for new key capacity admission; allocate UUID/time; encode/hash canonical payload; INSERT event; capture its actual SQL sequence immediately; construct/bound/encode record and immutable receipt; INSERT Host; INSERT existing idempotency; COMMIT; send receipt. Any precommit error rolls back all writes; ambiguous commit outcome reconciles the original key. Reads and valid replay generate no events/UUID/time sample. No schema activation, root manifest edit, Core wiring or native code is implemented or allocated here.

## Stable-key reconciliation precedes admission

For every authenticated, bounded and validated create, one IMMEDIATE transaction performs this order:

1. Read existing idempotency row for hosts.register:v1/key and any Host creation-key association. Do this before inventory count, name/sort handling, UUID/time allocation or any admission-side work.
2. Existing key plus unequal canonical payload returns CONFIG_CONFLICT even if the registry is full. Existing key plus equal payload returns the stored immutable receipt after bounded consistency checks against its Host row and creation event. A missing/malformed/mismatched associated row, sequence, event kind/revision/aggregate or payload returns a safe integrity/OUTCOME_UNKNOWN error; never silently recreate, repair or treat it as absent. Replaying a well-formed historical receipt does not re-check present capacity/name availability.
3. With neither receipt nor associated creation-key record, apply new-create capacity (proposed128 records). Names may repeat; there is no name-based replay or uniqueness admission. A Host row whose creation key exists without its idempotency row is ambiguous/corrupt, not a free key. No network/filesystem/identity resolution is part of admission.
4. Allocate a server UUID and event timestamp only for this new create, then atomically write the event, immutable Host row and idempotency receipt as described below. Commit before sending success.

A406be16 alignment supersedes B's initial unique-name proposal: names are not unique. The name_key is the exact already-validated UTF-8 display name, with binary/case-sensitive comparison for the proposed (name_key,id) index. V1 rejects leading/trailing whitespace, controls, empty names and names over256 UTF-8 bytes; therefore A's trimmed-name description equals the original validated name, without performing another transformation. Do not trim, case-fold or Unicode-normalize payload/display bytes. Same or similar names, case variants and Unicode byte variants may coexist; UUIDs distinguish them in UI and APIs. New key plus same name creates a separate UUID if capacity permits; it never returns another key's receipt. Sorting/index keys confer no identity or authority. Future search/uniqueness changes require an explicit reviewed contract/migration, without changing historical canonical payloads.

Registry host_id is generated by Core as UUID and is the primary reference for registry/get/UI records. It is distinct from endpoint.expected_host_identity, the bounded protocol identifier the user expects a companion to claim. The reserved builtin local record cannot be supplied, replaced or shadowed by a client UUID; the pure validator also rejects expected protocol identity local without claiming identity proof. Names and expected protocol IDs are not registry primary keys. Different names may intentionally describe the same expected protocol ID or endpoint; this cut does not automatically deduplicate, alias, migrate or share authority between them. An expected ID, known_hosts file digest, opaque identity ref or declared platform is not observed identity or a capability. Future authorized contact must independently bind its exact registered revision, SSH server-key evidence and companion identity; a UUID never substitutes for either remote proof.

## Lost response and read behavior

Commit success followed by socket/process loss is an unknown client outcome. hosts.find_registration accepts the original key in params as a read, even at capacity, without allocating IDs/events/keys, sampling time, resolving references or initiating contact. It returns found with the original receipt only after the same association checks. Absent means no matching durable receipt AND no associated Host creation record in the successful read snapshot. Database/open/version/read/integrity errors are not absent. An absent snapshot cannot prove an earlier in-flight operation will never commit: retrying hosts.register with the SAME key/body is safe; sending a new key is not justified by timeout, disconnect or absent alone. Retain a pending state while transport/storage recovery is unresolved.

hosts.get/list report stored metadata separately from server-derived facts: registration=registered, local_validation=configuration_syntax_validated at creation, references=unresolved, remote_probe=not_probed, remote_connection=not_contacted, remote_capabilities=unknown, execution_enabled=false. These are metadata-only scope facts; no last_seen or fake successful heartbeat is manufactured. This cut has no contact operation and must not overwrite future genuine observations with not_contacted: an unknown newer record/view version is VERSION_UNSUPPORTED, not silently downgraded. A daemon socket being connected says nothing about the remote Host. Reads do not invoke SshConfig::argv, Client, DNS, stat, companion Store, Provider or a remote filesystem.

Proposed list limit1..25, whole response at most512KiB, ordered by ascending created_sequence; positive after_created_sequence is an opaque local ordering cursor, not an authority token or event subscription. No OFFSET/unbounded scan or caller-chosen SQL order. At most128 records and16KiB metadata bound receipt/record decoding and response work. Unsupported record versions, invalid persisted metadata and missing linked events fail visibly; do not silently omit malformed records as if absent. These numerical Core bounds are proposed, not measured performance claims.

## Atomic record/event/idempotency persistence

Reuse the same Core Store and existing events/idempotency tables. Align with A406be16's exact proposed six-column table: id TEXT PRIMARY KEY, name TEXT NOT NULL, name_key TEXT NOT NULL, revision INTEGER NOT NULL CHECK(revision=1), created_sequence INTEGER NOT NULL UNIQUE REFERENCES events(sequence), document TEXT NOT NULL; one named nonunique index host_registrations_name_id(name_key,id). The FK has default NO ACTION, is not deferred, and has no CASCADE/SET NULL. No new creation_key SQL column/index or name uniqueness constraint is proposed after alignment. SQL mirrors and the closed versioned document must agree on generated UUID, original name/name_key, revision and actual sequence. This is a proposal, not permission to write DDL or add a second receipt store.

The versioned server document must additionally retain the immutable creation_key with fixed scope hosts.register:v1, created timestamp and registration metadata, plus only explicitly labeled creation-time syntax/unverified facts. The submitted metadata type itself remains unchanged; clients do not supply the server document. Retaining creation_key in the document allows bounded cross-checks if generic idempotency is missing. This trades a new indexed column for a bounded full Host-document consistency scan under the128-record cap. The fixed proposed shape and byte/work limits are pinned above and in registry-contract/CONTRACT.json for root review before S1/S3 tests; the SQL alone does not prove them.

Within one IMMEDIATE transaction, after replay/admission: generate Host ID; insert a redacted host.registered event with aggregate_id=Host UUID, revision=1, source=user_action and a bounded metadata/creation linkage payload; obtain the insert's actual events.sequence from the same transaction immediately; insert the Host row with that created_sequence and document creation_key; encode/insert the immutable receipt under hosts.register:v1/key in existing idempotency; commit. The events row's authoritative sequence is its SQL key, not an unbound sequence=0 inside a pre-insert event document. Build receipt/cursor from the actual inserted key. Do not use MAX(sequence), a connection-wide query after interleaving writes, or the helper that currently discards the sequence without extending its owned interface. Never wrap failed SQL in success or continue after an error.

There must be no durable outcome containing only an event, record or receipt. ID/sequence uniqueness, FK, encoding, disk/journal and commit failures roll back the whole transaction. If commit acknowledgement itself is uncertain, report OUTCOME_UNKNOWN and reconcile the same key on a usable Store; do not promise rollback merely because the caller saw an error. A successful new create yields exactly one Host, one creation event and one idempotency row. Same-key concurrency yields that same receipt; different keys with one exact name yield distinct UUIDs while capacity permits. Capacity-bound concurrent creates cannot exceed the cap and leave no losing event/receipt. Reopen/crash recovery must preserve this invariant under the existing private SQLite/WAL/FULL policy; no sidecar Host DB, scheduler or companion journal is added.

Existing generic idempotency has no FK columns. Therefore transactional writes, the document creation_key and bounded replay/read association checks are mandatory compensating invariants; existing generic helper replay alone is insufficient. For missing-key/association reconciliation, fetch at most129 Host rows, reject more than128 as integrity/resource error, and strictly decode/validate every bounded document while searching creation_key. Duplicated creation keys, malformed/version-unsupported records or mismatched SQL mirrors cause an error, never absent or a replacement create. Even a keyed receipt/record lookup needs consistency against its exact event and stored key/body. This is a bounded Host scan (up to128x16KiB metadata plus bounded server fields), not a whole-table event scan; fetch each needed event directly by created_sequence and compare kind/aggregate/revision plus linkage payload. The proposed24KiB document/receipt and4KiB event bounds above require implementation byte/work verification before acceptance. It must not reuse a512KiB response limit to silently truncate integrity reconciliation. The fixed event payload and receipt shape above must pass root review and future history/export tests before implementation acceptance; they permit these checks without storing credentials or inventing a native SSH public-key fingerprint from a file digest. A missing/mismatched reference does not grant repair/recreate authority.

## created_sequence, retention and eventual removal

created_sequence is a real FK to the durable creation event, not merely a list cursor. foreign_keys=ON must hold on every writer; test it and PRAGMA foreign_key_check after migration/reopen. Default NO ACTION with this immediate FK means event/history TTL cannot delete a Host's creation event, and must never cascade into deleting the Host registry or its receipt. This proposal pins the creation event while its immutable Host/receipt is live. Existing source audit found event-deletion fault fixtures, not a proven production Host-aware retention implementation; retention compatibility is pending, not claimed tested.

No retention/removal path is implemented here. Future log redaction/compaction must preserve the minimum event identity/linkage required for replay consistency and FK reachability, or introduce a reviewed durable tombstone/receipt-anchor migration first. Do not expire idempotency rows independently, since a forgotten key can turn a retry into a duplicate create; no receipt TTL is introduced. Retaining unbounded keys through repeated create/delete cycles is not solved by the current live-record cap: a future removal contract must also bound durable tombstone/receipt storage explicitly, without silently forgetting an ambiguous operation.

Future explicit user-approved Host removal must reconcile active attempts/references, history/privacy/retention pins and stable-key replay before any delete, atomically retaining a sufficient tombstone or replacing its FK anchors through an approved migration. Original submitted metadata may require deliberate redaction under a future privacy policy, but that cannot silently produce a different receipt on an old key. This unresolved design must be settled before adding removal or event compaction. Generic history expiry is never authority to delete source directories, native auth/config files, an external Host or original source files. Host registration itself adds no file ownership.

Migration19, existing current schema assertions and genuine historical/frozen18/inverse evidence are root/A's separate package. Keep native-run.py historical pin unchanged. A19 database cannot be made18 simply by lowering user_version while Host table/records/receipts/events remain. Any test inverse must enumerate/remove exactly its synthetic Host19 additions in an isolated fixture, preserve predecessor data and prove the intended old-reader rejection and true predecessor opening separately; no production downgrade API is proposed. Nonempty Host state and its references must not be silently discarded by a compatibility path.

## Required acceptance after explicit implementation scope

These are future tests, not results from this docs phase:

- Auth/version/closed envelope/params, actual raw IPC-frame and serialized Host-byte limits (distinguished from foundation raw decoder limits); no early-queue/model exposure; validate before persistence; no IO/contact/execution facts from metadata.
- Exact canonical golden payload and immutable receipt across new request IDs, restart and response loss; key conflicts win over capacity; equal-key replay works at128 records even with repeated names. Replay allocates no new UUID, timestamp, event or row.
- New-key repeated-name creates are distinct UUIDs; case/Unicode bytes stay unchanged; generated registry ID is distinct from duplicate expected protocol IDs, with no alias/upsert or active binding changes. Concurrent equal-key operations have one durable winner; concurrent different keys obey capacity without name-based authority.
- Inject event/Host/idempotency insert, serialization, disk/journal and commit failures, plus crash immediately before/after commit; reopen/reconcile proves zero-or-complete and no false absent after integrity/read failure. Preserve failed fault evidence.
- Corrupt/missing receipt, document creation-key association (including duplicate/corrupt/over-cap scan), Host/event/document version, linkage and FK; replay/find fail closed without repair. Missing keys during a still-in-flight create cannot trigger a new-key retry.
- Genuine18 backup, migration19, repeat reopen, rollback and future-version rejection before writes; FK checks, deletion restriction, atomicity and byte/cursor bounds. Historical18/native-run pin and exact current/inverse assertions stay truthful.
- Real Core IPC/native/UI vertical verification after shared paths are transferred, with missing daemon/error/reopen/lost-response states and no remote SSH, Provider, capability or full remote-product completion claim.

The only implemented evidence remains registration/AFTER.json:8 pure +18 prior Rust +16 actual subprocess fault tests against the recorded WIP bytes subsequently committed at cb5. No Core registry/migration/retention, cross-machine SSH/Linux, native or UI verification follows from this contract.
