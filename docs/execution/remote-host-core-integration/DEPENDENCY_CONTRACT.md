## Existing model and safety boundaries

There is no persistent Host registry/API in accepted Core. `registry.rs` models Projects, ManagedWorkspaces and fenced workspace leases. `sessions.rs:109` already distinguishes ProviderConnection's executable, environment_id, identity_ref, config_revision, host_id and capability snapshot. Registration fixes host_id=local (`sessions.rs:359`), identity unknown and version-probe-only approval. It is not a Host record. Native `connections_register` uses `confirm_proposed` and Connection approval because it can inspect/execute a local program; reusing it for remote Host metadata would conflate domains and could schedule a probe.

`policy.rs:234` admits only ready local Provider connections; `policy.rs:367` rejects nonlocal execution grants. `workspace_resolution.rs:239` and `task_workspace_binding.rs:241/296/372` restrict code preparation/bindings to local. These are **preserved**, not removed when a remote Host is registered. No new remote connection, Grant, recipient, routing candidate, active-attempt migration or task execution is enabled by inventory registration. Goal/App local-host guards remain in effect.

Core's one `storage::Store` owns SQLite plus event/idempotency transactions. Accepted database schema is18; `Store::open` rejects future versions before its migration writes, creates private backups, runs existing sequential migrations/recovery and uses WAL/FULL. No generic settings/Host table exists to reuse. Existing idempotency/approval/connection tables must not be misused as a separate Host datastore.

The UI path is `hosts-api` → fixed Tauri commands → authenticated private UDS IPC → the same Core Store. `App.tsx` Settings is the proposed single advanced disclosure entry, rather than a new task/terminal entry or Connections execution selector. Native Runtime/call is private and Tauri main capability contains no shell/filesystem plugin permissions. Preserve those restrictions; add only fixed command handlers in a child `hosts.rs` module and its handler list. Metadata-only registration performs no new external side effect or execution authority, so it need not introduce a new native Grant/Connection approval kind. Any later contact/provisioning/file access requires its own actual policy/authority integration.

## Proposed bounded registration/status contract

Core generates the registry UUID; reserved builtin Host id `local` cannot be supplied/overwritten. A bounded user-visible name and declared platform macOS/Linux are stored separately from expected remote protocol Host ID. Claimed platform is not observed OS support. Keep SSH transport identity reference separate from a Provider account identity, companion configuration ownership/reference separate from Provider RuntimeEnvironment, and logical remote directory mapping separate from any local Workspace path.

Proposed `HostRegistrationV1` contains strict closed/versioned metadata: name, declared platform, expected protocol Host ID, SSH endpoint(user/address/port/alias), approved known_hosts file **digest reference**/64-hex digest, opaque transport identity/config references, configuration ownership (Baton-managed or external-read-only declaration), and bounded logical mapping IDs to declared remote absolute roots. No passwords, tokens, private keys, authorization Grant, local source directory copy, arbitrary command or `connected/verified/enabled` fields. An SSH known_hosts-file SHA-256 is not an OpenSSH public-key fingerprint; names and UI text must keep these distinct.

Registration is an owner-authenticated reversible metadata write with a stable key. It validates serialized references/bounds and stores the record, local validation report, event and idempotent receipt atomically. Exact-key/same-body replay returns the same record; differing body conflicts. Proposed minimal methods: `hosts.register`, `hosts.list` (bounded page/cursor/byte budget), `hosts.get`, and `hosts.find_registration` for lost-response read-only recovery. Reads reject mutation-envelope fields. Install all Host dispatch arms only after the existing owner token/API/request-id checks (`ipc.rs:866`); do not expose them via a scoped/model tool handle or a new early-queue bypass. Keep existing actor/FIFO scheduling; registration is not an extra scheduler. Create-only immutable records are the initial minimum; in-place key/identity replacement is not silently permitted. Any later update requires explicit expected-revision semantics and drift rules.

Return server-derived facts, never trusted UI assertions: registration=registered; local_validation=configuration_syntax_validated or a specific safe error; key/identity/config references unresolved unless there is real evidence; remote_probe=not_probed; remote_capabilities=unknown; remote_connection=not_contacted; execution_enabled=false. UI must say which local checks actually ran; it must not label an opaque identity reference or stored key digest as verified identity. Refresh reads existing Core facts and never spawns SSH, resolves DNS, launches a companion, executes a version probe or samples an arbitrary filesystem path. Unsupported/future record versions fail closed and remain distinguishable from offline/failed/unknown.

Suggested engineering bounds (to validate, not an owner-approved performance promise):128 inventory records,25 per page and512KiB response budget,16KiB serialized record,8 mappings, remote root512 bytes, shared foundation identifiers64 bytes. Reject unknown fields/version, controls/NUL/traversal, reserved local identity, shell syntax in endpoint/fixed command parameters, duplicate mapping IDs, unintended local-to-remote absolute-path interpretation. Keep byte limits in addition to counts. Arbitrary metadata text is escaped and never executed; error payloads do not echo secrets or raw OS errors.

## Reusing RHOST-001 without running an attempt

Foundation `transport::SshConfig::argv` already enforces strict host-key options, fixed command and allowlisted strings, but it also reads an explicitly provisioned known_hosts file and stats identity files. `Client::{local,ssh}` spawn processes. `protocol::Config` is an attempt Grant (project/connection/attempt/input/config/identity/Host/budget/expiry) and `Store::open` writes a companion journal. None is a harmless registration constructor; do **not** invoke them from this task's registration/status read.

Propose a small pure `registration.rs` validator/typed endpoint definition in the existing foundation, factoring the current syntactic allowlists out of `SshConfig::argv` and retaining its existing file checks/strict options for future authorized transport. Core reuses only the pure validator; registration/status never uses `Client` or companion Store. No second scheduler, config synchronizer, grant authority or crypto is created. Pure checks do not prove files, DNS, key authenticity, remote directory/symlink state or Agent availability.

Root Core can depend on the independent `../remote-host` crate without adding it to root workspace members: propose one path dependency in `crates/core/Cargo.toml` and a serialized root Cargo.lock entry, using its already pinned versions. Leave remote-host's own [workspace]/lock and explicit verifier intact. Root Cargo.toml should not need a change. This dependency resolution is a static proposal, not a verified Cargo metadata/build result in phase1.

There is a future execution-binding mismatch to keep explicit: Core permits bounded512-byte refs and creates identity_ref `unknown:<uuid>`/capability `client-no-tools:<uuid>`, while foundation Binding uses64-byte alnum/underscore/hyphen IDs. Registration must not fabricate an attempt binding or strip/hash references to pretend compatibility. A future reviewed canonical-reference mapping and real identity/config proof are dependencies for execution, not requirements to weaken here.

## Persistence and schema dependency

Recommended implementation is a dedicated host_registrations table in the **existing Core database**, with indexed generated ID/name key and a closed versioned document; reuse existing events/idempotency in the same transaction. No independent Host DB/daemon or abuse of existing connection/approval rows. New schema is19, with a private genuine predecessor backup, atomic table/version migration, reopen/repeatability/corruption/rollback tests, and unknown-future rejection before write pragmas. Keep historical migration18 and genuine predecessor data intact.

This is a real cross-cut dependency: merely raising Store's upper bound is insufficient. Current exact18 checks exist in background_status, factory history/reads, integration target/read/budget/fence logic, native lib/background policy, frontend snapshot/background/TaskIntegration. Native smoke/owner fixture and strict evidence-source controls also assume18. `SOURCE_AUDIT.json` lists the actual literal paths/lines; historical/frozen18 fixtures are NOT automatically rewrite targets. Therefore schema19 compatibility/evidence closure must be assigned and serialized with the integration window before a runnable vertical cut. The minimal Host feature paths are concrete in PROPOSED_SCOPE.json, but the full migration/evidence closure cannot honestly be called just those few files.
