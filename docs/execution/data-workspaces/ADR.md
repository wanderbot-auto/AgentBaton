# ADR: explicit files and no-overwrite publication

Use a fixed, owner-approved file list instead of automatic recursive directory copying. Keep declarations and verified host tokens separate; JSON labels cannot grant path authority. Reserve the unique final directory atomically and publish an exclusive Ready marker only after complete source/copy checks. Never rename over unknown destinations or clean partial directories. Ready recovery trusts a host-authenticated persisted creation contract plus actual target bytes/permissions/root pins, independently of original source availability. Byte/stamp before-after checks are observations, not OS input freeze or atomic multi-file snapshot proof. Resource caps are explicit safety limits, not an MVP reduction.

The complete restore contract also fixes the identity of every created intermediate directory, so replacing a parent or making it public cannot preserve a verified result merely by keeping file bytes. Case-folded component names are checked across the entire selection, and all path pairs are checked for file/directory prefix conflicts. Filesystem-specific normalization collisions still fail exclusive directory/file creation; unknown existing contents are never reused.

A successful mkdir is the side-effect boundary. Failure to open/pin the new directory afterwards returns OutcomeUnknown with its reserved path rather than an ordinary pre-effect error. Errors with a still-matching private target may add an exclusive Failed observation, without removing any copied or owner-added file. No available free identifier is searched and no partial creation is resumed automatically.

Resource caps are64MiB/file,256MiB selected total,64 inputs,4MiB metadata,16 relative path components and4096 UTF-8 path bytes. Host callers may only tighten file/count/total limits. Dataset revision binds format, actual selected byte hashes/sizes, artifact IDs and explicit source/destination relative paths; source inode/approval labels are separate selection provenance, so identical content contracts have the same revision across source roots. Full restore digest includes that provenance, root/directory/file identities and creation ID. Hashes establish version observations, not authenticity, OS immutability or an atomic multi-file transaction. Reading may cause normal OS access-time updates; no source content/config/index/permission write is requested.

`from_verified_host` constructors are trusted library boundaries, not authentication. Future Core must authenticate native/CLI owner action and persist the fixed intent before calling copy, and authenticate the complete saved contract before restore. Agent JSON, a disk label or a caller-supplied approval string cannot substitute for that step. Known native-auth directory names and whole HOME are rejected defensively, but this is not general secret detection; the host must select legitimate dataset files. Restoration revalidates only this snapshot's selected inputs/metadata and permits unrelated later workspace outputs to exist without treating them as approved inputs.

Final publication now verifies the existing Creating record against the complete contract before writing Ready, then re-reads both records after syncing and before returning a verified token. This closes a missing observation during the operation, not a promise to block later same-UID writes. A private thread-local cfg(test)-only hook injects deterministic real file overwrites at the two publication boundaries; it does not exist in production. Saved old semantics actually fail both controls. Selection limits precede sorting/root I/O; restore record count/path/hash-shape checks precede building digest vectors or cloning completed records. Host-side DTO parsing still requires bounded transport/authentication at future Core integration; these constructors do not authenticate JSON.
