## Findings

### FR343-01 — P1 — scoped calls do not revalidate all original Grant bindings

Paths: `crates/core/src/factory_runtime.rs:155` (`live`), `:552` (`authenticate_factory_handle`).

Trigger: approve a root Grant covering more connection/workspace references than the narrower Factory selection, start a Factory session, then change an original Grant reference omitted from that narrower selection (configuration/identity/host/program/capability pin or workspace binding) without changing the persisted Grant document. Call one of the four scoped methods using the still-current private handle.

Evidence: authentication calls `live()`. That verifies checked Grant lineage and byte-equality of its stored document, then loops only through `FactoryScopeBindings.connections/workspaces`. It does not call original Grant live registered-binding validation across `grant.connection_bindings/workspace_bindings`. A changed omitted reference is therefore invisible to the scoped-call predicate. Session creation performs original Grant live validation, but that earlier check is not a substitute for each tool call; the scoped IPC handler has no such outer check. The Core author explicitly confirmed this gap in fixed343 and is preparing a separate fix.

Required fix: use the existing complete `validate_grant_live_from_with_data` contract at the live authentication boundary, with a genuine request-private data/workspace witness when required, or reject unsupported witness-less cases. Do not replace an absent private witness with a Factory/native boolean or lower the original Guard. Preserve bounded live filesystem checks without running repository Git/scripts in tool authentication. Add actual scoped-call drift negatives for original selected and omitted connections/workspaces, all relevant config/identity/host/program/capability fields, TTL/revocation/fence/attempt ownership, with no child/idempotency/events/resources admitted on denial. This is a new per-call runtime requirement, not a claim that the earlier selected-binding approval/start fix failed.

### FR343-02 — P1 — fanout join loses sibling handoffs and conflates child results with the parent's own result

Paths: `crates/core/src/factory_runtime.rs:1421`–1437; `:834`–853 (`factory_result`); prompt construction `:1226`.

Trigger: the live parent delegates two allowed children with different output IDs/artifact hashes, completes its turn and is truly stopped/joined. Child1 finishes, then child2 finishes. Existing allowed max_children/fanout contracts permit this scenario.

Evidence: the first child's settlement sees a remaining sibling and does not build a parent handoff. On the last child's settlement, `pending == 0` computes a digest over **only `b.result` for that last child**, then executes `parent.result = b.result.clone()`. It never collects the earlier completed siblings. New parent prompt sends only that `handoff_result`; the new native session is explicitly not a continuation of the old provider session. Earlier sibling result/attempt/hash references remain in separate DB records but are omitted from the delivered handoff.

The same storage assignment also makes a related public association error: while the parent is resuming, `get_task_result(parent_id)` unwraps `parent.result` and can return the copied **child task handle** and child `result_available` state as the parent's response. A handoff input is not the parent's own completed result.

Required fix: separate bound child-handoff/continuation inputs from each task's own result; aggregate the complete expected terminal-child set deterministically, preserving scope/run/parent/child/attempt and actual artifact/hash/validation references with a bounded digest. Enforce complete envelope limits and fail explicitly rather than omit siblings. Add a generated real two-child→new-parent case with distinct artifacts/attempts, and assert `get_task_result(parent).task.task_id == parent` throughout waiting/resuming and no false parent result availability or TaskAccepted.

### FR343-03 — P1 — cancelled never-dispatched children leave an unresolvable waiting parent

Paths: `crates/core/src/factory_runtime.rs:890`–923 (cancel pending child); `:1390`–1417 (parent settlement); `:1281`–1300 (next action); `:1421` (join pending count).

Trigger: during its initial active turn, a parent delegates a child and uses `cancel_task` to cancel that child before any child attempt exists. All children can be terminal-cancelled before the parent ends its turn. Parent then completes normally and its actual worker is joined.

Evidence: cancellation sets the never-dispatched child to `cancelled`/confirmed_stop. Parent settlement counts all `factory_delegations`, irrespective of child terminal state, so `can_wait = normal && children > 0 && round == 0` still changes parent/run to `waiting_child`. The scheduler excludes cancelled children. No future child worker settlement exists to enter the only join/resume code. Even if another sibling completes, the join predicate counts cancelled siblings as pending because it only excludes state `result_available`. The run is consequently left waiting without runnable or outstanding child work until unrelated cancellation/expiry intervenes.

Required fix: centralize terminal-child join/reconciliation after parent stop and after each child cancellation/settlement. Model cancelled/failed/unknown child outcomes explicitly; choose a bounded failure/continuation or terminal run policy, without promoting cancellation to successful artifact production, refunding consumed history or launching a cancelled child. Add actual four-tool delegate→cancel-never-dispatched-child→parent-completion and mixed completed/cancelled siblings cases; verify no child process/resource admission and no impossible waiting state.

### FR343-04 — P2 — scoped requests bypass the normal expired-ready-request check

Path: `crates/core/src/ipc.rs:1604`–1619.

Trigger: a scoped mutation waits in the shared request queue beyond `ReadyRequest.deadline` while the scope/Grant itself is still live. Actor work can currently delay queue service; the known large-artifact responsiveness issue is already being fixed separately.

Evidence: `handle_ready_request` detects any `scoped_token`, calls `handle_factory_scoped`, sends the response and returns **before** the common `Instant::now() > job.deadline` gate. All four scoped operations therefore bypass the ordinary60-second queue admission expiry. Authentication may still pass and a queued delegation/cancel mutation can commit after this ready-request budget expires. This is first late execution, not a claim of automatic retry.

Required fix: apply the common queued-request expiry predicate before either dispatch route, or an equivalent scoped gate. Preserve outcome-unknown/idempotency reconciliation and never generate a new mutation key automatically. Add a controlled expired queued scoped mutation proving no child/idempotency/event changes. This belongs to the already-existing preflight/queue workstream; no separate task or blocking-load experiment was started here.

## Important positive boundaries observed statically

- `FactoryCaller`/`FactoryDispatchContext` are private Core contexts. Requests contain selection/target IDs, not caller/root/parent/attempt/fence authority. Handle lookup uses a token SHA256 digest, expiry/revocation, stored run/scope/session/attempt/task/project/root correspondence and exact workspace lease holder/fencing token. Descendant target access is checked through same-run binding and checked ancestry; child connection/workspace and input/output IDs must be subsets, with bounded depth/fanout/total nodes and narrower budgets. FR343-01 remains the missing complete Grant revalidation.
- The scoped envelope uses deny_unknown_fields and only `delegate_task`, `get_task_status`, `get_task_result`, `cancel_task`. It cannot pass the ordinary owner-token Request shape or use approval/configuration/arbitrary IPC through the scoped route. The companion also advertises/allows exactly four initialized tools. Existing tests' approvals.finalize attempt is rejected by the bridge whitelist; that observation alone is not a full daemon-forged-envelope negative suite.
- CLI enters `factory-mcp PATH` before calling default_runtime_dir/ordinary `ipc::call`. Companion code reads only its explicit scoped credential, never the global owner token. Tokens are random private file content; DB stores their digest and public handle metadata, not the token. Normal events/DTOs do not contain the token. The credential file's socket selector necessarily reveals the runtime path; this code is not an OS/same-UID filesystem sandbox, as the false guarantee fields already acknowledge.
- Issuance creates/checks an owned canonical0700 handle directory and exclusive0600 nofollow leaf. Companion reads that file with descriptor-relative nofollow traversal, owner/mode/nlink/byte bounds and stable file metadata. Companion executable bytes are hash-checked against the approved canonical program; provider projection contains only fixed `factory-mcp` argv plus the private file path and empty MCP env. A caller-supplied arbitrary MCP command/env/server is not accepted by this projection. External/native config is not written. Same-user mutation between a pathname verification and a separate provider's eventual exec is not a claimed kernel FD-execution sandbox.
- Session admission keeps command fences, unreconciled-writer/lease refusal, original Grant and ancestor attempt/concurrency limits, shared root/project counters and local supervisor max4. Factory session roots derive from the private context, and ordinary sessions cannot independently dispatch Factory task lineage. Per-task/ancestor runtime/output reservations count prior attempts and retain unknown usage instead of resetting to0. Mixed ordinary/Goal/Factory accounting still needs actual tests; these static hooks do not establish its correctness.
- Supervisor processes a completed worker only after `thread.is_finished()` and a real `join()`. Receipt persistence then requires owned process-reaped or never-started evidence before confirming intent stop/releasing the workspace lease. Normal Factory handoff additionally requires the matching internal completed-turn receipt and no current cancellation. A cancellation request is not itself a join/lease release. Restart marks ambiguous runs unknown and revokes old handles; failed/malformed/unknown settlement does not become accepted output or automatic new attempt.
- Artifact references are selected paths with actual observed hashes/lengths after stop; results set acceptance_state `not_established` and validation_refs empty. There is no TaskAccepted/Git adoption permission from this path. Reading an existing selected file after a child stops does not itself prove that child authored the file or that it passed correctness validation. FR343-02 still requires correct task association and complete sibling handoff.
