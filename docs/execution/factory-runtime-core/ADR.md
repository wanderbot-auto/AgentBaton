# Independent Task delegation, unchanged execution grants

Factory approval grants bounded Task decomposition only. It is not a retrospective upgrade of an existing Goal scope or ExecutionGrant. Initial descendants reuse the same unchanged root ExecutionGrant and existing approved connection/workspace; ancestor, project, root, host and global execution limits remain applicable. ExecutionGrant.max_depth/max_children still constrain Grant derivation, not Factory Task trees. The original delegate_grant API continues rejecting depth0 grants. Factory has its own independently approved Task depth, per-parent fanout and total-node ceilings; each child further narrows the parent Task budget. A legacy Goal or Grant alone cannot mint a scoped handle or child Task.

The approval snapshot shows both the unchanged original grant and the new Task-delegation capability with distinct authority labels. Future new-workspace, child Goal or child planning capabilities require their explicit complete contracts; the initial unsupported fields are rejected, never silently activated. Starting is a separate idempotent action after approval. Approval alone starts neither Provider nor MCP companion.

The fixed companion receives only a private per-session credential reference, never the daemon's general token. Four scoped methods are independent of owner IPC. A request's caller/root/project/attempt/fence come from the checked handle. Renderer-controlled fields, Provider names, repository instructions and tool output cannot supply these identities. All selected source snapshots and handoffs remain point-in-time observations, not an OS sandbox, DLP or continuous freeze.

A waiting label never releases an actual process, lease or reservation. Initial execution is sequential: parent completes its turn and is truly reaped, then child runs, then a new parent attempt consumes explicit, hash-bound handoff references. This does not claim native context restoration. Unknown processes or effects stay fenced across restart and are not retried with a new key.

### Cooperative Data observation and worker elapsed

Reuse existing safe restore with a host-only cancellation/deadline restriction between bounded64KiB reads; keep legacy API and nofollow/marker/identity/hash rules. Pending Factory observation watches are server-derived stop metadata, never caller authority. Ownercancel/revoke operates after durable control commit using only owned in-memory cancellation metadata, without demanding a successful witness. Actual joins remain prerequisites to freeing worker concurrency; kernel I/O cannot be forcibly interrupted. All worker paths, including never-started boundary refusal, share one elapsed footer so metadata/preflight time is not silently refunded. Witness-independent history/stop paths remain separate from allfour Agent methods, which always require full fresh original Grant/Data proof.

### Request-owned Factory Owner read observations

Factory Owner propose/finalize/start may hash approved inputs and a bounded fixed companion image. Those reads run in the existing bounded Data I/O worker using a separately opened read-only, query-only SQLite transaction. This worker never opens Store through its migration/recovery API, writes business rows, or grants authority. The Actor captures the exact relevant business rows before delegation. The returned private, non-Deserialize observation binds those rows, the database/parent identities, original raw request hash, original deadline, selection, approved companion path, all held file identities and the complete server-resolved bindings. The Actor rechecks business rows, current Grant/expiry/CAS, Data witness and bounded filesystem metadata before its normal authoritative transaction. An observation is usable only by this request; it is not a reusable approval cache. Historical exact-key replies require no new observation and do not restart the runtime queue clock.

Keeping only selected input and Git HEAD/index/config observations is insufficient: an unselected tracked-file edit or a newly created untracked file can invalidate the worker's clean-worktree result without changing those pins. The returned observation therefore also covers the whole observed work tree of every Git workspace in the original Grant, plus loose refs/common metadata. It includes ignored entries conservatively rather than claiming to reproduce Git exclude semantics. All these trees share strict limits: 8192 entries, 256 held directory descriptors, 1MiB total entry-name bytes, and depth64. The worker enumerates via directory descriptors and nofollow stat, rejecting special/multilink leaves and explicit resource overflow; the Actor does not enumerate directories, execute Git, or read/hash file contents. It rechecks held directory stamps and each captured entry with descriptor-relative metadata calls, including before/after directory stamps. This is a bounded point-in-time observation, not continuous freezing or protection against a privileged filesystem adversary. Large/ignored-heavy repositories can be refused explicitly; they are never silently partially observed.

SQLite proof budgets are shared across the entire projection (4MiB raw values and 100000 rows, with a per-query1MiB limit). Each query's raw lengths and count consume the remaining budget before values are materialized. The private DB path, ownership, mode0600, single-link identity and parent0700 are pinned and rechecked. Owner/internal stop paths remain independent of a successful read. Merely declining an unsupported approval kind does not gain a new authority path or journal receipt.
