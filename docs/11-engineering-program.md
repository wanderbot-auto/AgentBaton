# 11 · 面向完整产品的长程工程程序

## 1. 完整目标与执行方式

目标是实现获批的完整 AgentBaton，而不是把目标退化成三个页面。长程任务必须分解为可追踪、可恢复、能独立验证的工作包；这些是依赖关系和交付证据单元，**不设周数、天数、短期冲刺或固定迭代期限**。

采用 specification → approved decisions → dependency graph → scoped execution → evidence → acceptance 的链路。未完成项保留原始需求 ID，禁止为了“完成全部”删掉难点或把 mock 改名为真实集成。

## 3. 工作包内部闭环

读取相关需求与决策 → 检查环境/接口 → 写执行计划与假设 → 实施可测试纵切 → 运行正常/失败/安全测试 → 独立审查 → 更新证据和兼容矩阵 → 标记验证层级 → 提交审查。

一项纵切必须跨过必要的契约、实现、界面与验证，而不只是创建空目录和TODO。可以在长程任务中连续完成多个 ready 包，前提是授权、预算、环境和依赖满足；不承诺单次无限执行或自动跨任务续跑。

## 4. 并行工作约束

不同任务使用独立 branch/worktree；共同 schema 或公共状态机由单一 owner 改动，其他任务等待接口批准或基于固定版本。代码所有权声明避免两个 Agent 同时修改同一迁移/锁文件/全局进度表。

每任务写独立 progress/evidence 文件，由集成者合并。集成前检查 base revision；合并后重跑相关验证。worker 分支绿不代表集成分支绿。

## 5. 执行授权与范围

本包提供完整设计，但默认 execution authorization 为 `review_only`，直到用户创建带真实资源与范围授权的执行任务。批准的工作包可持续实施，已确认的是产品应具备的托管、路由和交付行为，不是当前对任何真实仓库/Host/数据的操作授权。真实执行必须有目标、资源、预算与分支范围；生产发布、未授权付费、签名凭据及具体许可选择不可自批。

实施过程中碰到局部未知，可记录并继续独立工作。遇到修改核心契约、改变用户数据路径或越过安全边界的决定必须形成决策请求，不以“默认同意”填空。

## 6. 进度与证据

记录 `specified → approved → implementing → implemented → mock_verified → provider_verified / platform_verified → accepted`，具体验证维度按需求适用。用状态和证据说明，不用模型估算的百分比。

每条报告链接 req_id、package_id、commit、运行环境、命令、exit code、测试摘要、产物与已知限制。尚未运行就是 not_run，阻塞就是 blocked。报告不能覆盖原始失败记录。

## 7. 上下文和重启恢复

保存 PLAN、CHECKPOINT、DECISIONS、PROGRESS 和 evidence manifest。新的 Codex任务先读checkpoint，再检查实际 Git/测试状态与版本，避免把过期报告当真。任务环境不是永远存在的记忆；未提交修改不得假设自动传给下次任务。[S01]

AGENTS.md保持短且指向文档，详细规范按需读取。官方文档支持分层项目指令，而长程任务实践强调规范、执行计划、验证与持续记录；本包借鉴的是这些原则，不宣称外部平台自动执行本工作流。[S02][S19]

## 8. 停止与不确定性

停止新副作用的条件：授权缺失；严格权限无法落实；同类修复达到预算；真实集成需人工登录；签名/发布缺凭据；无法确认已执行外部操作；无法保留检查点。安全落盘后报告最后可确认状态和下一步。

任务被平台结束、额度耗尽或用户终止后，不承诺自行恢复。继续运行需要真实新任务、继续指令或已配置的触发器。产品设计完整不等于允许无限算力、无限子任务和无限重试。
